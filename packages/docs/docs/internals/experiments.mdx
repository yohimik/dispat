# Release experiments

These experiments run release tools against disposable Git repositories and a real local npm registry. They show
what remains after a partial publication and what each tool does on retry. The separate [coverage](./coverage.mdx),
[test results](./test-results.mdx), and [benchmarks](./benchmarks.mdx) pages describe the automated suite.

<ReportStamp />

<ExperimentsSummary />

The protocols cover three failures: a registry rejects one package, a colleague pushes while the release is running,
or a consumer fails after its provider has published. Each experiment records the local checkout, remote Git refs,
and registry versions before making a recovery claim.

The fixture has six npm packages. `cli`, `ui`, and `api` depend on `core`; `theme` and `docs` depend on `ui`.
All six start at version 1.0.0, tagged and published. The original publication and push-race protocols use a minor
change to `core` with tilde dependency ranges. The propagation protocol uses a patch-compatible correction so it can
separate explicit propagation intent from a dependency range that needs updating.

The base fixture gives every package one `build` script. The `build` and `publish` propagation cells run that same
script as dispat's build stage and as Lerna's `lerna run build`; the Changesets cells run it explicitly. The
`deferred` cell removes `cli`'s build command to isolate delivery after an own release, while `deferred-build` keeps
the actual build. The baseline tags are annotated, because `git describe` ignores a lightweight tag and a tool that reads its
previous release that way would otherwise find no release at all and treat every package as changed.

By default, each cell runs the binary from `yohimik/dispat-alpine:<version>`. A prepublication run can supply a candidate
executable and an explicit identity, which is recorded in its verdict. A local Verdaccio registry sits behind a proxy
that can reject uploads for one named package while forwarding other requests. These runs use no public registry,
and every cell has its own registry state.

## Records first, verdicts second

A cell records what a tool left behind in the three places a release writes: the local clone, the origin, and the
registry. After every step of the protocol, those three are read and joined into one state per package.

For dispat, some of those readings are expectations, and a cell that misses one fails the release that ran it. For
lerna, nx and changesets the same readings are recorded either way. A row below that reads 3/5 is a description of that
tool under this fault, not a failure of the run and not a claim that the tool is broken: the expectations are dispat's
own, written from what dispat promises, and holding another tool to a promise it never made would be a comparison of
nothing.

## By experiment

<ExperimentsTable />

The final state column is the answer per package at the end of the run, in this vocabulary:

| State        | Meaning                                                                         |
|--------------|---------------------------------------------------------------------------------|
| `consistent` | the registry's version is tagged on origin and the tag is reachable from `main` |
| `orphan`     | a tag names a version the registry does not hold                                |
| `unpushed`   | the tag exists in the local clone only                                          |
| `dangling`   | the tag is on origin but outside `main`'s ancestry                              |
| `unrecorded` | the registry serves a version no tag names                                      |
| `baseline`   | nothing beyond the fixture's 1.0.0, so the row is left out                      |

`dangling` is what a rebase after a refused push produces: the release commit is rewritten, the tags stay on the
original, and the next plan of a tag-driven tool sees everything as changed again. `orphan` is what tagging before
publishing produces: the tag says a version shipped that nobody can install.

Each reading also records the manifest the checkout holds at that moment, its version and its dependency ranges. The
registry says what shipped and the tags say what was recorded; a range a release reconciled, or a version rewrite it
rolled back, appears in neither.

The `build` and `publish` propagation cells start with a patch to `core` that remains inside the consumers' `~1.0.0` dependency
range, so semver alone asks for no consumer release. Dispat receives `fix(core)^: correct reader`, whose caret is
explicit propagation intent. Lerna receives the plain `fix(core): correct reader` and decides for itself: nothing is
forced on its side, and what its version command selects is part of the record. Changesets receives explicit patch
entries for `core` and its three direct consumers, the closest way to request the same release set with that tool.

The release sets differ. Dispat releases `core` and its three declared consumers, writing each consumer's range up to
the provider it shipped with. Lerna releases all six, because it bumps every transitive dependent of a changed
package, `theme` and `docs` included, although `~1.0.0` already accepted `core@1.0.1`.

The provider is published and observed before the consumer's fault is injected. Under Lerna the protocol
publishes `core` and reads the registry before arming the fault. Under Changesets the operator runs `core`'s build and
`npm publish` from that package's folder; `changeset publish` does not provide a provider-first build stage. Under
dispat one command runs the whole release, so
the fixture sets `isBuildWaitingPublish: true` on `core`, which holds every consumer's build until the provider is
published; the protocol reads that ordering back out of the run's own log.

The `build` scenario fails `cli`'s build script, and the record shows that `cli` never reached a publication attempt.
The `publish` scenario lets the build succeed and has the registry refuse the upload. Both faults are the same script
and the same registry under both tools, so the two scenarios separate a failed build from a refused publication rather
than naming one failure twice.

After the fault is removed, no commit is made and no new release intent is supplied. Dispat's next plan contains the
owed `cli` catch-up alone, its recovery publishes `cli` without republishing `core`, and the plan after it is empty.
Lerna's tag-based `lerna changed` is already empty, because its version command tagged every package before any was
published; `lerna publish from-package` then queries the registry and republishes the five packages it finds missing,
rather than the one that failed. Changesets' status is empty after its `version` command consumes the changeset file;
`changeset publish` queries the registry and publishes the remaining `cli`, `ui` and `api`. It does not tag `core`,
which the operator published separately before the fault, so that provider is still unrecorded in this protocol.

The Dispat-only `deferred` cell tests a further edge: `cli` has no build command and publishes its own fix after `core` fails, then an operator
releases `core`, `ui` and `api` on the next run while leaving `cli` out. With no new source commit, the next full plan must catch up `cli` from the
provider's durable publication, and the run after that must be empty. The earlier `cli` tag already contains the
propagation commit, so the pending commit window alone cannot reveal this debt.

The `deferred-build` companion keeps `cli`'s actual build script. When it has already built over the planned provider
version, Dispat withholds it with `W194` after the provider fails; the next run rebuilds and publishes the consumer's
own pending fix against the version that really shipped. It tests the artifact safety boundary beside the no-build
delivery-receipt case.

The colleague's push lands at a point in the tool's own sequence rather than on a timer. A shim placed first on `PATH`
for the duration of the release command records every git call the tool makes and fires the colleague's commit and push
once, right before the first `git push` that is neither the release lock's nor a commit. The interleaving is therefore
the same every time and the same for every tool, and where in the release it falls is part of the record: lerna commits
and tags and then pushes both, nx pushes before it commits or tags, changesets makes no push of its own so the push is
the operator's, and dispat publishes first and pushes last.

The comparison this measures against the documented behaviour of each tool is in
[beside other release tools](/comparison#the-experiments).

## Reproducing

Every cell is one container, and the whole campaign is one command from the repository root:

```sh
EXPERIMENTS_DISPAT_VERSION=1.7.1 dispat exec experiments --for pkg:experiments --in pkg:experiments
dispat exec summary --for pkg:experiments --in pkg:experiments
```

One cell at a time, for re-recording a single protocol:

```sh
EXPERIMENT=midrelease TOOL=dispat SCENARIO=conflict \
  dispat exec experiment --for pkg:experiments --in pkg:experiments
```

| Variable                      | What it does                                                                    |
|-------------------------------|---------------------------------------------------------------------------------|
| `EXPERIMENTS_DISPAT_VERSION`  | the released version to run against; the newest published image when unset      |
| `EXPERIMENTS_DISPAT_ARTIFACT` | an unpublished candidate executable to copy into the experiment image           |
| `EXPERIMENTS_DISPAT_ID`       | required immutable identity recorded when a candidate executable is supplied    |
| `EXPERIMENTS_RESULTS`         | where the records land; `coverage/experiments` at the repository root by default |
| `EXPERIMENTS_JOBS`            | how many cells run at once, four by default                                     |
| `EXPERIMENTS_EXPECT`          | `0` records a dispat cell without gating on its verdict                         |

Each cell leaves a folder with the transcript, every step's output, one observation per step, every failed
expectation's own output, the registry's logs, the git calls the tool made, and `verdict.json`. The harness itself, the
fixture, the observer and the fault proxy are documented in
[`tests/experiments/README.md`](https://github.com/yohimik/dispat/blob/main/tests/experiments/README.md).

The release workflow carries forward a completed campaign when the published native image and harness are identical.
The docs package's `beforeBuild` hook checks the image id, exact cell list, every verdict and observation stream, and
every dispat verdict before reuse. A new binary or protocol, or a missing, corrupt, partial or failed record, reruns
every campaign cell. This page is built from the validated records. The
[Experiments workflow](https://github.com/yohimik/dispat/actions/workflows/experiments.yml) uses the same generated cell list on
demand, for any released version.

## What this is for

These are not benchmarks and they are not a scoreboard. They exist because the claims dispat makes about recovery are
claims about failure, and a claim about failure that has only ever been tested against a stub is a claim about the
stub. Publishing before tagging, re-running rather than querying a registry, joining a branch that moved instead of
refusing it: each of those is a sentence in the documentation, and each of these cells is that sentence executed
against a registry and a remote that really do refuse.

The compared tools are here for the same reason a control is: a result that only ever ran against one tool cannot say
whether what it measured was the tool or the fixture. Running four tools through one fixture with one fault says which
differences are the tools'.
