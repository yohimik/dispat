# Release experiments

These experiments run release tools against disposable Git repositories and a real local npm registry. They show
what remains after a partial publication and what each tool does on retry. The separate [coverage](./coverage.mdx),
[test results](./test-results.mdx), and [benchmarks](./benchmarks.mdx) pages describe the automated suite.

<ReportStamp />

<ExperimentsSummary />

The protocols cover three failures: a registry rejects one package, a colleague pushes while the release is running,
or a consumer fails after its provider has published. Each experiment records the local checkout, remote Git refs,
and registry versions before making a recovery claim. A fourth experiment injects no fault: it times each tool's plan
and release, and sets each tool's plan beside dispat's.

The fault protocols share a fixture of six npm packages. `cli`, `ui`, and `api` depend on `core`; `theme` and `docs`
depend on `ui`. All six start at version 1.0.0, tagged and published; the timing experiment adds a second, wider shape,
described [below](#planning-and-release-time). The original publication and push-race protocols use a minor
change to `core` with tilde dependency ranges. The propagation protocol uses a patch-compatible correction so it can
separate explicit propagation intent from a dependency range that needs updating.

The base fixture gives every package one `build` script. The propagation and timing cells run it where each tool
documents a build: dispat's build stage, nx's `release.version.preVersionCommand`, and the `prepack` script that
`lerna publish` and `changeset publish` run for every package they pack. A failed build is therefore one fault seen
through four tools. The publication and push-race cells run no build under lerna, nx or changesets. The baseline tags are annotated,
because `git describe` ignores a lightweight tag and a tool that reads its previous release that way would otherwise
find no release at all and treat every package as changed.

By default, each cell runs the binary from `yohimik/dispat-alpine:<version>`. A prepublication run can supply a candidate
executable and an explicit identity, which is recorded in its verdict. A local Verdaccio registry sits behind a proxy
that can reject uploads for one named package while forwarding other requests. These runs use no public registry,
and every cell has its own registry state.

## Records first, verdicts second

A cell records what a tool left behind in the three places a release writes: the local clone, the origin, and the
registry. After every step of the protocol, those three are read and joined into one state per package.

For dispat, some observations are release requirements: a missed expectation fails the release running the experiment.
For lerna, nx, and changesets, the harness records the same observations without treating them as requirements. A
score such as 3/5 shows how that tool behaved under this particular fault. The expectations come from dispat's contract
and may not be promises the other tool makes.

The injected fault must actually occur. If it does not, the harness fails the cell and does not publish its row.

## By experiment

<ExperimentsTable />

The final state column is the answer per package at the end of the run, in this vocabulary:

| State        | Meaning                                                                         |
|--------------|---------------------------------------------------------------------------------|
| `consistent` | the registry's version is tagged on origin and the tag is reachable from `main` |
| `orphan`     | a tag names a version the registry does not hold                                |
| `unpushed`   | the tag exists in the local clone only                                          |
| `dangling`   | the tag is on origin but outside `main`'s ancestry                              |
| `unrecorded` | the registry serves a version no tag names                                      |
| `baseline`   | nothing beyond the fixture's 1.0.0, so the row is left out                      |

`dangling` is what a rebase after a refused push produces: the release commit is rewritten, the tags stay on the
original, and the next plan of a tag-driven tool sees everything as changed again. `orphan` is what tagging before
publishing produces: the tag says a version shipped that nobody can install.

Each reading also records the manifest the checkout holds at that moment, its version and its dependency ranges. The
registry says what shipped and the tags say what was recorded; a range a release reconciled, or a version rewrite it
rolled back, appears in neither.

### Propagation and recovery scenarios

The `build` and `publish` propagation cells start with a patch to `core` that remains inside the consumers' `~1.0.0`
dependency range, so semver alone asks for no consumer release. dispat receives `fix(core)^: correct reader`, whose
caret is explicit propagation intent. lerna and nx receive the plain `fix(core): correct reader` and decide for
themselves: nothing is forced on their side, and what their version step selects is part of the record. changesets
receives explicit patch entries for `core` and its three direct consumers, the closest way to request the same release
set with that tool.

The release sets differ. dispat releases `core` and its three declared consumers, writing each consumer's range up to
the provider it shipped with. lerna and nx release all six, because they bump every transitive dependent of a changed
package, `theme` and `docs` included, although `~1.0.0` already accepted `core@1.0.1`.

The fault is armed before the first run, and each tool runs its own documented release with nothing published by hand:
`dispat release`; `lerna version` and then `lerna publish from-git`; `nx release`; `changeset version`, a commit and
then `changeset publish`. The `build` scenario fails `cli`'s build script, and the `publish` scenario lets the build
succeed and has the registry refuse `cli`'s upload. Where each tool builds decides what its first run publishes.
dispat's fixture sets `isBuildWaitingPublish: true` on `core`, which holds every consumer's build until the provider is
published, and the protocol reads that order back out of the run's own log. lerna runs every package's `prepack`
before it publishes any, and nx runs its pre-version command before it versions, so under the `build` fault neither
publishes anything in its first run. changesets publishes the missing packages side by side, so `core`, `ui` and `api`
publish while `cli` fails.

After the fault is removed, no commit is made and no new release intent is supplied, and each tool takes its own
documented recovery. dispat runs the same command again. lerna runs `lerna publish from-package`, which publishes
whatever the registry is missing; it first refuses the working tree its own failed publish left rewritten, so the
protocol checks the manifests out by hand and runs it again. nx runs `nx release publish` for what its first run
versioned, or `nx release` again when it versioned nothing, and the release commit nx leaves on the clone is pushed by
hand. changesets runs `changeset publish` again, and the operator pushes what it tagged.

Five more scenarios reach the same catch-up through other ways a consumer comes to be owed its provider, and every
tool runs each of them. Under dispat, `build-distributed` repeats the `build` fault with every build on a worker node,
which the release reaches through the repository being released: `execution.choreographers` names `build-a` and
the command advertises its authenticated return endpoint. Its record matches the local cell's, and its log names the worker that ran `cli`'s build. In `deselected` the
first run is `dispat release --package core,ui,api`, so `cli` sits the provider's release out. In `held`, `cli` is held
by a `Release-As: none` commit while `core` ships, and the operator resumes it with `Release-As: auto` before the
catch-up. In each, the next full run has to find what `cli` is owed from the provider's release alone.

The `deferred` cell tests a further edge: `cli` has no build command and publishes its own fix after `core` fails, then
the operator commits once and releases `core`, `ui` and `api` while leaving `cli` out. With no new source commit, the
next full plan must catch up `cli` from the provider's durable publication, and the run after that must be empty. The
earlier `cli` tag already contains the propagation commit, so the pending commit window alone cannot reveal this debt.
The `deferred-build` companion keeps `cli`'s actual build, and the fault proxy holds the provider's refusal until
`cli`'s build output exists, so `cli` has always built over the provider's planned version when the provider fails.
dispat withholds that artifact with `W194`, and the catch-up rebuilds and publishes the consumer's own pending fix
against the version that really shipped.

lerna, nx and changesets take the same scenarios through their nearest mechanism, and where a tool has none, the
protocol runs its ordinary release and the transcript says so. None of them has a self-hosted worker, so their
`build-distributed` cells repeat the `build` protocol: nx distributes tasks only through Nx Cloud, which the harness
disables. In `deselected`, nx runs `nx release --projects core,ui,api` and changesets runs
`changeset version --ignore cli`; `lerna version` takes no package selection, so lerna's first run is unselected. In
`held`, the hold is a committed edit the operator reverses before the catch-up: `cli` marked private with
`--no-private` on every `lerna version`, `["*", "!cli"]` as nx's `release.projects`, and `cli` in changesets' `ignore`
list. changesets refuses a changeset that names an ignored package beside others, so in these two scenarios its
fixture asks for the same four patches in two files. In `deferred` and `deferred-build`, `cli` commits a fix of its own
before the provider's fix, and in `deferred` it has no build script, because these tools run every build they find.
After the refused first run, nx releases the provider with `--projects core,ui,api`, while lerna and changesets
publish whatever the registry is missing, because their publish commands take no selection. A `deselected` or `held`
catch-up is the tool's own release again; a `deferred` catch-up is the recovery the `build` protocol uses. nx runs
`nx release publish` instead whenever a version it tagged is missing from the registry. These rows are held to
dispat's sentences about what shipped, never to dispat's own diagnostic codes.

### A push during the release

The colleague's push lands at a point in the tool's own sequence rather than on a timer. A shim placed first on `PATH`
for the duration of the release command records every git call the tool makes and fires the colleague's commit and push
once, right before the first `git push` that is neither the release lock's nor a commit. The interleaving is therefore
the same every time and the same for every tool, and where in the release it falls is part of the record: lerna commits
and tags and then pushes both, nx pushes before it commits or tags, changesets makes no push of its own so the push is
the operator's, and dispat publishes first and pushes last.

The comparison this measures against the documented behaviour of each tool is in
[beside other release tools](/comparison#the-experiments).

## Reading the Catch-up column

The Catch-up column counts the work needed to finish after the fault was removed. It separates release commands from
manual steps such as a checkout, commit, or push. Read-only checks such as `dispat status` or `lerna changed` are not
counted. A run is an uninterrupted sequence of the tool's commands; a failed command or manual step ends that run.

| Reading                        | Meaning                                                                            |
|--------------------------------|------------------------------------------------------------------------------------|
| `1 run, 1 command`             | one of the tool's own commands finished the release                                |
| `1 run, 2 commands, 1 manual`  | one pass of the tool's commands and one step done by hand                          |
| `2 runs, 3 commands, 1 manual` | a failed command or a step done by hand interrupted the tool, and it ran again     |
| `none needed`                  | the catch-up ran nothing, because the release had already converged                |
| `not measured`                 | the protocol measures no catch-up, as the push-race cells do                       |

A reading ends in `did not converge` when the release did not end settled. A release converged when every package is
consistent or at its baseline, the local clone is clean and level with its origin, and the tool's own next plan is
empty: `dispat status --require-release` finds nothing to release, `lerna changed` lists no package,
`nx release --dry-run` writes no new version, and `changeset status` lists no package to bump.

The propagation cells ask every tool the same questions about it: whether the plan before the catch-up named the owed
consumer, whether the catch-up took one run and no manual step, whether the consumer shipped at the version first
planned, whether the provider was published once, and whether the release converged.

## Planning and release time

The `timing` cells run each tool's own plan command and then its documented release, with no fault, and time both.
The `six` scenario is the six-package fixture with its pending minor to `core`. The `wide` scenario is a generated
fixture of the same kind with many more packages: `core`, a short chain of packages each depending on the one before
it, and a row of leaves depending on `core` alone, so a release of all of them has a short longest chain beside a large
total. Each tool is told of the change the way it reads one, and the Plans table below prints what each cell's tool
was told, from the record.

<ExperimentsTimingTable />

**Planning** is the duration of the tool's plan command: `dispat status`, `lerna version` with nothing committed,
tagged or pushed in a scratch clone (lerna has no dry run), `nx release --dry-run`, and `changeset status --verbose`.
Each runs as it is. nx's dry run also runs its pre-version command, and the Tasks table counts the builds that ran
inside each plan command. **Makespan** runs from the start of the release's first command to the end of its last:
`dispat release`; `lerna version` and `lerna publish from-git`; `nx release` and the push of the commit it leaves on
the clone; `changeset version`, the commit, `changeset publish` and the push. **Idle** is the part of the makespan in
which no task was running.

The tasks are timed by the fixture and the registry, never read from a tool's log, so all four tools are measured by
one clock and one definition of a task. A task is a build or a publication, and nothing else. Every build writes a
line with its start and end, and holds for a fixed time first so it lasts as long as a short compile rather than as
long as node takes to start. Every publication is timed as its upload, from the moment the registry's proxy receives
the request to the moment the registry answers, because the upload is the one point every tool's publication passes
through: lerna publishes in-process, and the others through `npm publish`. What a publication timed at the registry
leaves out is the client's side of it: node starting, packing, and preparing the request. Those, and every tool's
versioning, commits, tags and pushes, fall outside the tasks under all four tools alike, and show in the idle time and
the ratio rather than in Wk. An `npm` shim first on `PATH` during the release also times every `npm publish` process
whole, with its own package's build cut out; the Tasks table shows those beside the uploads, and they are no part of
Wk or Lk.

<ExperimentsTasksTable />

The figures are those of the [dispat theorem](https://github.com/yohimik/dispat/blob/main/specs/ccme-spec/SPEC.md#1311-complexity-and-scale)
(CCME specification §13.11). **Wk** is the summed duration of the release's tasks and **Lk** the duration of the
longest precedence chain through them. **s** here is the most tasks the release was seen running at one instant: an
observed concurrency, not the theorem's count of task slots usable at once. With s read that way, **max(Lk, Wk / s)**,
the bound, is a time no execution of the plan beats that honours its precedence and runs at most that many tasks at
once with these measured durations, and the ratio is the makespan over it.

The precedence is the plan's: every package builds before it publishes, a provider publishes before its consumer
(§19.2), and what a consumer's build waits for of its providers is the build readiness relation (§19.2a): their
publications (`publish`), their builds (`build`) or nothing (`none`). The relation is declared, never inferred, so each
cell is measured under the one its tool's configuration declares. dispat's fixture leaves `isBuildWaitingPublish` at
its default, `false`, which is `build`. `lerna publish` packs every package, running its `prepack` build, in dependency
order before it publishes any, which is `build`. The nx fixture's pre-version command is `nx run-many -t build`, and
its `nx.json` declares no `dependsOn` for the build target, so nx orders no build after another: `none`.
`changeset publish` publishes in chunks of the dependency graph, each after the one before, and npm runs a package's
`prepack` build inside its own `npm publish`, so a consumer builds after its providers have published: `publish`.

Each cell's records are then held to that precedence edge by edge. The Relation column prints the declared relation,
and beside it, where they differ, the strongest relation every consumer build in the records honoured. The Edges not
honoured column lists every edge of the declared precedence a task started before the task it follows had ended. The
bound holds only for an execution that honours its precedence, so a row with an edge listed there has a bound that is
not a lower bound of its own release, and the report refuses a row with no edge listed whose makespan is shorter than
its bound by more than the clocks' slack.

A ratio of 1 is a release that took no longer than its own tasks allowed at the concurrency it used. Clause 2 of the
theorem gives the `(2 - 1/s)` bound for identical usable slots, a work-conserving schedule that never leaves a slot
idle while a task is ready, and no additional resource restriction. Observed peak concurrency alone does not
establish those premises, so exceeding that ratio is not by itself a theorem violation or proof of scheduler idle
time. The Idle column measures how much of the makespan had no task running at all. The bound is each tool's own: a tool whose relation
makes a consumer build wait for more has a longer Lk to be measured against, so read the ratio beside the makespan.
The ratio is also relative to the concurrency each release used, so a release that ran its tasks one at a time has
the whole work as its bound and can read close to 1 while taking longest.

Every timing cell is one container on a shared host, run after every other cell of the campaign and one at a time, so
no other cell runs beside it. Tasks that run at once still share the container's processors, so a release that runs
many tasks at once also stretches each of them; the Tasks table shows each kind's median and longest. Report elapsed
time for this recorded workload and host alongside each tool's ratio. Ratios use different graphs, measured durations
and observed concurrency, so they do not rank cross-tool speed. Absolute seconds describe the machine the table names.

<ExperimentsPlanTable />

Every tool's plan is read from its own plan command's output as a set of packages at their next versions; dispat's
own count of the packages it is releasing is held against that reading. dispat's plan of the same scenario is the
reference, and each row says whether the tool's plan names the same packages at the same versions, or which differ:
`also` for packages only that tool releases, `not` for packages only dispat releases, and a version beside dispat's
where both release a package at different versions. The Told column is the input each tool read, and the reference is
only as wide as the input dispat was given: where dispat's commit asks for direct consumers alone and another tool
releases every transitive consumer on its own, the difference is that choice of input, read from the Told column, not
two readings of one instruction. A difference is a record of what each tool decided from what it was told, not a
verdict on which decision is right. Every timing cell then checks its release against its own plan: the release
exited 0, shipped every package the plan named at the version it named, shipped nothing else, left every shipped
package consistent, and honoured every edge of the precedence it was measured under. A cell whose records miss a
shipped package's build or upload, name a package outside the fixture, or cross the release's start or end is not a
record, and the harness fails it rather than publishing figures over it.

## Reproducing

Every cell is one container, and the whole campaign is one command from the repository root:

```sh
EXPERIMENTS_DISPAT_VERSION=1.7.1 dispat exec experiments --for pkg:experiments --in pkg:experiments
dispat exec summary --for pkg:experiments --in pkg:experiments
```

One cell at a time, for re-recording a single protocol:

```sh
EXPERIMENT=midrelease TOOL=dispat SCENARIO=conflict \
  dispat exec experiment --for pkg:experiments --in pkg:experiments
```

| Variable                      | What it does                                                                    |
|-------------------------------|---------------------------------------------------------------------------------|
| `EXPERIMENTS_DISPAT_VERSION`  | the released version to run against; the newest published image when unset      |
| `EXPERIMENTS_DISPAT_ARTIFACT` | an unpublished candidate executable to copy into the experiment image           |
| `EXPERIMENTS_DISPAT_ID`       | required immutable identity recorded when a candidate executable is supplied    |
| `EXPERIMENTS_RESULTS`         | where the records land; `coverage/experiments` at the repository root by default |
| `EXPERIMENTS_JOBS`            | how many cells run at once, four by default                                     |
| `EXPERIMENTS_EXPECT`          | `0` records a dispat cell without gating on its verdict                         |

Each cell leaves a folder with the transcript, every step's output, one observation per step, every failed
expectation's own output, the registry's logs, the git calls the tool made, and `verdict.json`. A timing cell also
leaves its timing records, `timing.jsonl`, its figures, `timing.json`, and the plan it read, `plan.json`. The harness itself, the
fixture, the observer and the fault proxy are documented in
[`tests/experiments/README.md`](https://github.com/yohimik/dispat/blob/main/tests/experiments/README.md).

The release workflow carries forward a completed campaign when the published native image and harness are identical.
The docs package's `beforeBuild` hook checks the image id, exact cell list, every verdict and observation stream, and
every dispat verdict before reuse. A new binary or protocol, or a missing, corrupt, partial or failed record, reruns
every campaign cell. This page is built from the validated records, and only the release workflow writes them: a run
by hand, as above, measures any released version without reaching this page.

## What this is for

The experiments check documented recovery behavior against a registry and Git remote that can really reject writes.
They cover details such as publishing before tagging, retrying an incomplete release, and recovering from a branch
that moved during the run.

Running other tools through the same fixture helps distinguish tool behavior from fixture behavior. The results
describe these versions, configurations, and fault scenarios; they are not a general ranking of release tools.

## LLVM distributed build

<ExperimentsLLVMTable />

The LLVM campaign compares Dispat's `compilation`, `interpretation`, and `hybrid` modes with Nx and Lerna's
Nx Cloud distribution. Changesets has no distributed build executor, so its entry is `unsupported`.
Nx and Lerna entries are `blocked` when a connected Nx Cloud workspace and credentials are unavailable; they
do not run locally or receive a duration in that case. These entries are availability results, not speed results.
See the [Nx Cloud commands](https://nx.dev/docs/reference/nx-cloud-cli),
[Lerna distribution documentation](https://lerna.js.org/docs/features/distribute-tasks), and
[Changesets CLI reference](https://changesets.dev/guide/cli).

The default `full` profile builds LLVM core's default libraries and tools twice, with X86 and AArch64 backends
in separate clean CMake/Ninja build directories. Both configurations use
[LLVM 20.1.8's pinned source](https://github.com/llvm/llvm-project/commit/87f0227cb60147a26a1eeb4fb06e3b505e9c7261).
This is two complete backend configurations, not a single LLVM build split at individual compiler invocations.
Clang, other LLVM subprojects, runtimes, tests, benchmarks, examples, and documentation are excluded identically.
The optional `smoke` profile builds only `llvm-cxxfilt` and `llvm-size`; its records explicitly identify that subset.

Each cell has two executor processes with separate task checkouts on one host, one active build per executor,
and the same Ninja job limit. These results measure distribution across processes, including coordination and
artifact transfer; they do not model a network between physical hosts. Source acquisition and toolchain installation
finish before timing, including Nx Cloud client acquisition in the coordinator and both agents. The harness
requires identical client versions and SHA-256 fingerprints and records them in the result. The clock starts
before executor startup and coordination, and stops after the coordinator
verifies returned executable digests, LLVM versions, and a demangling result. The full profile returns five
representative executables for these checks, while building the complete configured target. Every task contains a
fresh committed run identity, preventing another cell's cached output from satisfying a cold-build measurement.

Run `dispat exec llvm-experiments --for pkg:experiments --in pkg:experiments` after the release experiment campaign,
then use the ordinary `summary` script. The docs release hook runs this sequence automatically; the six LLVM
records go into the same report. Standalone cells default to four hours; the release workflow applies the same
45-minute cap to every cell within its six-hour job budget. The result records that cap, and an actual executor
failure prevents publishing the report. Blocked and unsupported entries remain unmeasured. Set
`EXPERIMENTS_LLVM_PROFILE=smoke` for harness validation. Nx Cloud cells use the existing `NX_CLOUD_ACCESS_TOKEN`
and `EXPERIMENTS_NX_CLOUD_ID` environment variables; the harness never writes the token into its fixture or report.
