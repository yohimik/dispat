# Test coverage

<ReportStamp />

<CoverageSummary />

The report measures statement coverage for the CLI and all six current public Go modules. Unit profiles come from
module tests. Integration profiles come from CLI runs against disposable repositories and public API scenarios that
combine parsing, configuration, scanning, and rewriting. The current CCME module uses its own public API driver
because the CLI still depends on the previous major version internally.

## Reading the totals

Unit and integration coverage are reported separately. Combined coverage counts a statement once if either layer
executes it, and supplies the README badge.

A stable release requires both integration and combined coverage to reach 95%. Unit tests cannot satisfy the
integration gate. Release candidates publish their figures without that minimum.

Before calculating a total, the report checks that every expected module and production block is present and that
profile provenance matches the run. Missing profiles, mixed revisions, and omitted subpackages fail the report rather
than reducing its denominator.
The badge and this page are therefore the same number, taken from the same run: the one that gated the release which
published this site.

The container cache may reuse a profile when the complete test input layer is byte-for-byte identical: the module,
its workspace providers, test-report tool and declared fixtures all participate in that key. A following layer stamps
the current source commit only after that identity check. The stamp therefore says the measurement applies to this
commit; it does not claim the test process ran again merely because documentation changed. A changed test input misses
the cached layer and runs the suite before it can receive a fresh stamp.

## By module

Coverage measures executed statements, not whether every requirement is correct. The requirement matrix also
tracks release-safety cases such as lock failure, interrupted publication, configuration inheritance, and consumer
recovery. An uncovered statement may represent a missing workflow or an error path; inspect the profile before deciding
whether a new test is useful. A high combined percentage does not prove the integration gate passed.
The per-package test inventory (what each package's suite actually asserts) is in
[Architecture / Testing](./architecture.md#testing), and what the suite did rather than what it reached is in
[test results](./test-results.mdx).

## Reproducing

Run these commands from the monorepo root to collect the same reports as the release workflow:

```sh
dispat run tests --since all   # every module's profile and go test -json log, into coverage/
dispat exec coverage-badge     # merges the profiles; writes the badge JSON and the summary table
dispat exec test-report        # writes packages/docs/data/report.json, read by this page
```

Every one of them is a build of `Dockerfile.gotest`, so none needs a Go toolchain on the machine running it.

Use `--since all` to include every module. A narrower window tests only selected packages and cannot produce a complete
repository total. The release workflow calculates the badge; the per-commit test workflow does not.

Rebuilding this site with `packages/docs/data/report.json` in place is what puts the figures back on the page; without
one, the prose stays and the tables are left out.

## What each layer contributes

Module tests exercise focused behavior, using both real resources and test doubles where appropriate. The
[CLI integration suite](https://github.com/yohimik/dispat/blob/main/tests/integration/README.md) drives the compiled binary
and checks Git state, log events, execution order, signals, and recovery. Its public API scenarios scan manifests,
rewrite them, and rescan the result, including failures that must preserve the original files.

`DISPAT_COVERDIR` enables CLI coverage collection, while the test runner collects public API coverage. Without these
settings, ordinary local tests run without coverage instrumentation. The release gate collects both sources into one
integration profile and compares its production statement inventory with the unit profiles.
The suite's own status and per-area summary are in [test results](./test-results.mdx), with the claim-by-claim matrix
in the [test plan](https://github.com/yohimik/dispat/blob/main/tests/integration/docs/test-plan.md).
