# Benchmarks

These measurements track execution time and allocations. For passing tests and statement coverage, see
[test results](./test-results.mdx) and [coverage](./coverage.mdx).

<ReportStamp />

<BenchmarkSummary />

Every number in the generated report below comes from a benchmark stream. A benchmark pass runs
`go test -run '^$' -bench . -benchmem`
per module, in a stage of its own, and the release folds the stream into the same report the coverage and test-results
pages read. The generated report preserves the measured runner and revision; the dated comparison below separately states
its fixture, toolchain and source revisions.

`-run '^$'` skips the ordinary tests during this pass. `-benchtime` uses Go's default, so the benchmark tool chooses
the measurement duration.

The benchmark stages are cached by the module source, workspace providers and reporting tool they contain. A docs-only
commit reuses the identical stream; a source, dependency or harness change runs the benchmark again. The report names
the publishing commit while retaining the runner and timestamp recorded by the actual benchmark process.

## Nested chain windows: before and after

`BenchmarkComputeChainWindows` builds one real Git chain with `P` distinct stable boundaries and one later scoped
change per package. Every commit has the same primary author, so the author output is linear in `P` while the
pending windows have quadratic logical membership. The comparison used the same fixture and ten measured iterations
per case on Apple M5, macOS arm64, Go 1.26.0. The before column is production revision `1460e93f` with only the
benchmark file added; the after column is implementation revision `ccb6c9d15c71`. Both ran through `testreport bench` with
`-C services/dispat -run '^$' -bench '^BenchmarkComputeChainWindows$' -benchtime=10x -benchmem ./internal/plan`.

| Packages | Author visits/op before → after | Allocated B/op before → after | Sampled peak heap MiB before → after |
| ---: | ---: | ---: | ---: |
| 64 | 6,112 → 127 | 881,732 → 859,935 | 0.3867 → 0.2651 |
| 128 | 24,512 → 255 | 1,626,112 → 1,577,108 | 0.8587 → 0.7957 |
| 256 | 98,176 → 511 | 3,172,186 → 3,049,360 | 1.840 → 1.879 |

The author-visit counter measures the changed subphase directly: the nested windows' separate scans are replaced
by one scan through the largest changed prefix. `WindowCommitRefs/op` remains 6,112, 24,512 and 98,176 respectively;
it counts logical window membership, not allocated bitsets. Peak heap is sampled and varies, as the 256-package row
shows. These measurements do not establish a time or space bound for the complete planner. To reproduce the before
column, add only the benchmark file to revision `1460e93f` and run the command above; run it again at the landed
implementation revision for the after column.

A row is one benchmark function, or one case of a table-driven one, named as its source names it. The iteration count
is a column rather than a footnote because it is what says how much to trust the row beside it: a benchmark the tool
ran ten times and one it ran ten million times are not the same kind of number. The machine is stated per module for
the same reason. A nanosecond figure without the CPU that produced it is a number nobody can compare anything to, and
a release runner is not a workstation.

Allocation counts help catch regressions with less dependence on machine speed than timings. Several packages also
enforce allocation budgets in tests, with one allocation of headroom for toolchain differences. Those tests catch
changes such as an unnecessary copy being added back.

## Fuzz targets

<FuzzTable />

A plain `go test` replays each fuzz target's corpus: its `f.Add` seeds and the regression inputs in `testdata/fuzz`.
The corpus column counts those inputs. This pass does not run a new fuzzing session.

To run a fuzzing session, choose a target and duration:

```sh
go test ./... -run '^$' -fuzz FuzzParse -fuzztime 10m
```

A crash it finds is written into `testdata/fuzz` as a new corpus entry, committed, and from then on every run of the
ordinary suite replays it. That is why the corpus grows and why the count above is worth reading: it is the number of
inputs the suite is holding the parsers to, not the number of inputs anyone has tried.

## Reproducing

The whole measurement is one command per module from the monorepo root, and it is the one the release runs:

```sh
go run github.com/yohimik/dispat/tools/testreport bench config -- ./... -run '^$' -bench . -benchmem
go run github.com/yohimik/dispat/tools/testreport build   # writes packages/docs/data/report.json, read by this page
```

The stream lands in `coverage/benchlog/<module>.json`, beside the `go test -json` logs the suites leave in
`coverage/testlog/`. A module measured by a run replaces whatever it had; a module the run did not measure keeps it, so
a release that rebuilt only part of the monorepo does not blank a page. Rebuilding this site with
`packages/docs/data/report.json` in place is what puts the figures back; without one, the prose stays and the tables
are left out.

## What a benchmark here is for

These benchmarks track specific regression risks: an extra document copy, an unnecessary intermediate map, or an
allocation inside a loop. Where a test enforces a corresponding allocation budget, exceeding it fails the build.

The results measure dispat's code and test harness. They do not compare performance with other libraries.
